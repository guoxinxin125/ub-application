 关键信息：**内核模块版本相同、用户态工具相同、系统环境相同，但内核日志显示 `primary dev not exist, node 1 dev 1 die 0`**。

这说明 **`-EPERM` 是内核模块内部返回的**，不是系统权限问题，而是 **urma/uburma 内核模块在初始化时因为 `primary dev` 找不到，导致后续 netlink 通信时拒绝服务**。

---

## 核心问题：`primary dev` 为什么是 `node 1 dev 1 die 0` 而不是 `bonding_dev_0`？

| 正常机器 | 故障机器 |
|---|---|
| `primary dev` = `bonding_dev_0` (DEV 0) | `primary dev` 指向 `node 1 dev 1 die 0` (DEV 1) |
| topo 只有 1 个 DEV | topo 有 36 个 DEV (0-35) |

**故障机器的 `primary dev` 被错误地指向了 DEV 1（那个多余的 GID 设备），而不是 DEV 0 的 `bonding_dev_0`。**

## 推测

最可能的情况：

| 场景 | 说明 |
|---|---|
| qemu 验证时通过 `ioctl` 向 `/dev/uburma` 写入了 `primary_dev` 配置 | 配置持久化在驱动内部或固件中 |
| `bonding_dev_0` 的某些属性被修改 | 导致驱动不再将其识别为 primary |
| 驱动内部有一个 `primary_dev` 的索引/指针 | 被错误地指向了 DEV 1 |

## 可能的解决方案

### 方案一：查找并重置 primary dev 配置

```bash
# 查看是否有 sysfs 接口可以设置 primary
find /sys/class/uburma/ -name "*primary*" -o -name "*master*" 2>/dev/null

# 尝试通过 sysfs 重置
echo "bonding_dev_0" | sudo tee /sys/class/uburma/primary_dev 2>/dev/null
# 或类似接口
```

### 方案二：彻底清理并重新初始化 urma

```bash
# 1. 卸载所有 urma 相关模块
sudo modprobe -r urma
sudo modprobe -r uburma
sudo modprobe -r ub

# 2. 检查是否有持久化数据需要清理
sudo rm -f /var/lib/urma/* 2>/dev/null
sudo rm -f /run/urma/* 2>/dev/null

# 3. 重新加载（按正确顺序）
sudo modprobe ub
sudo modprobe uburma
sudo modprobe urma

# 4. 验证
urma_admin show topo
```

### 方案三：如果模块内部有缓存，可能需要重启

```bash
# 检查是否有内核缓存需要清理
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches  # 仅清理页缓存，不影响驱动

# 或尝试
sudo reboot
```
